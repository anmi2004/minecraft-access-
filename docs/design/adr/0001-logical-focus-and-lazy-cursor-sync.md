# ADR 0001：逻辑焦点与延迟光标同步

## 背景

当前背包导航用真实鼠标作为焦点。每次方向移动都通过 SDL 改变光标，再等待 Minecraft 或原版控件产生叙述。

配方书暴露了这一设计的根本问题：

- 配方 `SlotItem` 没有直接语义。
- 配方朗读依赖按钮 hover。
- 一个按钮包含多个结果时，需要通过鼠标抖动触发轮换结果的朗读。
- 第二页之后存在不可见但仍可导航的配方按钮。
- 翻页使用后台 `Timer` 延迟移动鼠标。

用户明确要求：

- 保持现有合成朗读。
- 一个槽位中多个配方变体变化时，仍能及时朗读。
- 朗读时正常直接朗读。
- 使用 `[`、`]` 等鼠标动作手势时，默认先把鼠标移到当前逻辑目标，再执行原操作。

## 决定

背包交互采用“逻辑焦点 + 延迟光标同步”：

1. 方向导航只改变 Minecraft Access 的逻辑焦点。
2. 焦点变化时直接调用现有屏幕阅读器。
3. 不因导航移动硬件鼠标。
4. 动作手势到来时，在客户端主线程把光标同步到逻辑目标。
5. 同步后继续复用原版鼠标 press/release 和容器操作路径。
6. 配方按钮使用独立变体跟踪器读取 `getDisplayStack()`；变体变化后直接朗读。
7. 所有延迟都使用客户端 tick 状态机，不使用 `java.util.Timer`。
8. 配方书横向越界只报告左侧或右侧没有项目；只有纵向 `I/K` 越出顶行或底行时才自动翻页。

## 理由

### 保留原功能

动作最终仍走原版鼠标和容器代码，不需要一次重写所有点击、拖动和长按语义。对未知模组界面的风险较小。

### 满足即时导航

语音不再依赖鼠标是否成功进入控件、原版是否触发叙述或按钮是否可见。普通槽位和配方都能直接构造朗读文本。

### 满足实时变体朗读

原版配方按钮的 `time / 30` 轮换逻辑保持不变。变体跟踪器只观察当前已显示结果，在变化后立即朗读，因此不伪造尚不可见的变体。

### 可测试

导航、朗读、光标移动和鼠标点击成为可分别观察的事件。测试可以断言顺序，而不是依赖真实鼠标最终位置。

## 后果

### 正面

- 导航延迟不再受鼠标 hover 和 RecipeButton 抖动影响。
- 第二页空白按钮可以从模型中排除。
- 配方变体朗读与视觉显示同步。
- 点击仍保持高兼容性。
- 可以逐步替换为直接控件动作。
- 保留现有横向边界提示，不需要改变方向图语义。

### 负面

- 动作前最多增加一个客户端 tick 的光标同步窗口。
- 必须处理快速点按、长按和焦点失效状态。
- 必须抑制同步触发的重复 hover 朗读。
- 需要为 Screen 结构变化定义刷新和焦点恢复策略。

### 兼容边界

- 如果某个第三方 Screen 对即时鼠标操作有特殊假设，可切换到直接动作适配器或虚拟光标兜底。
- 原版 GUI 内部方法变化时，动作桥仍应尽量依赖公开鼠标路径。
- 核心行为必须在公共源码实现；Fabric 和 NeoForge 只在确有 API 差异时增加薄适配器。
- 单加载器专属的分类元数据只能增强名称，不能成为导航、分页或操作的必要条件。

## 被拒绝的替代方案

### 全部直接调用 `slotClicked`

时序最短，但需要逐一适配第三方控件，且拖放和长按风险较高。保留为后续优化，不作为第一步。

### 继续优化鼠标优先

无法消除 hover 依赖、第二页空白按钮和线程问题，因此拒绝。

### 冻结配方按钮当前变体

会改变原版视觉和功能。要求是及时播报变化，不是禁止变化，因此拒绝。

### 缩短原版配方轮换周期

会改变所有玩家的原版行为，且仍无法保证叙述来源可靠，因此拒绝。

## 验证条件

此 ADR 的实现只有同时满足以下条件才算完成：

- 导航阶段真实鼠标移动次数为 0。
- 普通槽位焦点变化立即朗读。
- 配方变体变化在一个客户端 tick 内朗读。
- 动作手势严格按 move、press、release 顺序执行。
- 配方书最后一页不存在不可见焦点。
- `J/L` 在边界不改变页面，`I/K` 在纵向边界自动翻页并优先保留列。
- 背包控制关闭时原有悬停朗读不受影响。
- 容器、创造背包和配方书 GameTest 通过。
