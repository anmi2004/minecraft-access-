# 交互方案研究

## 评估目标

方案必须同时满足：

- 保持现有槽位点击、拿取、半组、放置、交换和拖放语义。
- 导航时立即朗读。
- 配方按钮中的多个变体按原版节奏变化，并在出现时及时朗读。
- 配方书翻页、分类、过滤和搜索可用。
- 模组或未知界面仍有兜底路径。
- 不引入跨线程 GUI 操作。

## 方案 A：继续使用鼠标优先

保持当前导航与点击都通过硬件鼠标。

优点：

- 最大程度复用原版鼠标路径。
- 对未知控件兼容性最好。
- 改动表面最小。

缺点：

- 导航仍依赖 hover 触发。
- 配方书延迟、第二页静默和抖动补丁继续存在。
- 每 150 ms 重建模型和 Timer 线程风险不消失。
- 鼠标物理位置与逻辑焦点持续耦合。

结论：不满足即时朗读目标。

## 方案 B：逻辑焦点 + 全部直接操作

槽位、按钮和配方全部通过原版内部调用执行动作，例如直接调用 `slotClicked` 或 `Widget.onPress`。

优点：

- 不移动鼠标。
- 操作路径最短。
- 时序可预测，容易测试。

缺点：

- 每个第三方控件都需要专用适配器。
- 鼠标拖放、长按和某些 UI 状态难以完全复刻。
- 原版 GUI 升级后内部方法容易变化。
- 一次性替换所有操作会扩大原功能回归风险。

结论：可作为长期适配器，不适合作为第一步的唯一路径。

## 方案 C：内部虚拟光标 + 吸附点

参考 Controlify：

- 内部保存虚拟光标坐标。
- 为槽位、按钮和配方按钮生成中心吸附点。
- 停止操纵摇杆时吸附到最近目标。
- 点击时通过内部鼠标处理发出事件。

优点：

- 对任意视觉控件通用。
- 不需要把硬件鼠标用于导航。
- 可配置吸附半径，精度高。

缺点：

- 注意力仍以坐标为中心，而不是语义目标。
- 仅移动到按钮不能自动产生可靠的朗读。
- 对纯键盘“上一项/下一项”不是最自然的交互。

结论：适合作为未知界面兜底，不适合取代语义组和方向导航。

## 方案 D：逻辑焦点 + 延迟光标同步

这是用户提出、本次推荐的方案：

1. `I/K/J/L` 只改变逻辑焦点。
2. 每次焦点变化直接构造文本并朗读。
3. 按下 `[`、`]`、`\` 时，先把硬件光标同步到当前逻辑目标。
4. 同步完成后继续沿用原版鼠标按下、释放和点击。
5. 配方按钮在逻辑焦点内独立监听当前变体，不依赖悬停。

优点：

- 保留原版点击语义。
- 导航和朗读不再依赖鼠标 hover。
- 配方书延迟不再受“鼠标必须停留并触发叙述”限制。
- 可由客户端 tick 状态机替代 Timer，消除线程问题。
- 可逐步将常用控件升级为直接操作，不强制一次性重写。

缺点：

- 点击比纯直接操作多一次光标同步。
- 必须谨慎处理“按下后立即释放”的快速手势。
- 需要抑制同步触发的重复悬停朗读。

结论：满足原功能不变和即时朗读要求，实施风险最低。

## 方案 E：配方搜索或列表循环

项目 issue #337 提议在合成台直接显示可制作配方列表：

1. 打开合成台。
2. 在列表中上下选择配方。
3. 激活后自动合成并说明产物位置。

优点：

- 比二维配方书网格更高效。
- 更适合反复合成。
- 朗读内容可以按“结果、原料、数量、可制作状态”组织。

缺点：

- 不是原版配方书，需要新的 UI 语义和交互契约。
- 涉及材料放置、数量选择和消耗确认。
- 应作为独立工作流，不能作为修复原配方书的替代品。

结论：适合作为第二阶段效率增强。

## 方案 F：外部配方查看器集成

项目 issue #274 讨论了 JEI/REI 等配方查看器：

- 覆盖原版配方书不支持的第三方模组配方。
- 提供搜索、分类和配方详情。
- 通常与多个 Screen 同时存在，破坏“只有一个 Screen”的假设。

可能路径：

- 建立可选适配器，发现配方查看器时暴露语义列表和动作。
- 通过稳定的公开 API 或受控适配层集成。
- 不依赖反射扫描内部控件。

结论：价值高，但依赖选择和跨版本稳定性差，应拆成独立设计。

## 成熟模组对照

### Controlify

Controlify 把问题拆成两层：

- Screen Operation：使用原版 `nextFocusPath/changeFocus` 处理普通控件焦点。
- Virtual Mouse：容器槽位通过内部虚拟光标和吸附点定位。

其吸附点包括：

- 每个 `Slot` 中心，半径 17。
- 配方分类按钮中心。
- 过滤按钮中心。
- 20 个配方按钮中心。
- 配方前后页按钮。

容器操作直接调用 `slotClicked(..., ContainerInput.PICKUP/QUICK_MOVE)`。配方页和分类也有专用按钮处理。

Controlify 的 GameTest 验证了：

- 配方书可见。
- 多页存在。
- 前后页切换。
- 分类向前和向后切换。

因此成熟做法不是“更平滑地移动系统鼠标”，而是：

- 导航状态独立。
- 目标有吸附点或焦点。
- 动作有明确适配器。
- 关键路径有 GameTest。

### MidnightControls

MidnightControls 的容器方向键使用 `findClosestSlot(direction)`：

- 计算当前鼠标或槽位位置。
- 在指定方向上寻找最近槽位。
- 把目标坐标排队，再通过 `MouseHandler.onMove` 更新。
- 操作时直接调用 `slotClicked`，不再模拟真实鼠标按钮。

它还用虚拟光标和径向/吸附逻辑帮助控制器选择槽位。

优点：离散选择准确，槽位点击路径直接。

局限：核心仍是坐标模型，且不是专门的屏幕阅读器项目；叙事可访问性仍需 Minecraft Access 自己实现。

## 方案比较

| 维度 | A 鼠标优先 | B 全部直接操作 | C 虚拟光标吸附 | D 逻辑焦点+延迟同步 | E 搜索列表 |
|---|---:|---:|---:|---:|---:|
| 原版点击兼容 | 最高 | 中 | 高 | 最高 | 新语义 |
| 导航即时朗读 | 低 | 高 | 中 | 高 | 高 |
| 配方变体及时朗读 | 低 | 高 | 中 | 高 | 高 |
| 未知界面兼容 | 中 | 低 | 高 | 中高 | 低 |
| 实施风险 | 低但缺陷保留 | 高 | 中 | 中低 | 高 |
| 可测试性 | 低 | 高 | 中高 | 高 | 高 |

## 推荐组合

基线采用方案 D：

- 逻辑焦点负责导航和朗读。
- 动作手势执行前同步真实光标，再沿用原版鼠标操作。
- 配方按钮通过变体跟踪器直接朗读。

后续渐进增强：

- 常用槽位动作可使用方案 B 的直接适配器降低操作延迟。
- 未知屏幕使用方案 C 的内部虚拟光标。
- 高频合成使用方案 E 的配方列表。
- 第三方配方查看器通过方案 F 独立集成。
